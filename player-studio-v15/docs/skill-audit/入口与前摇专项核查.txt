结论

1. 射门的真实随机偏差生成函数已定位。现有重炮修改的两个函数属于失误类别评分，并非最终射偏角度。实际误差还包括方向、仰角、球速三个不同输出，以及之后的条件性修正，不能用两个评分乘 0.8 代替“射偏统一减少 20%”。
2. 真正的加速属性输入已接到实际跑动动作执行链：0x6f4d714 读取比赛属性 44，0x6f40154 消费其结果选择跑动动作并下发播放参数，最终由 0x6dc4400 的 AnimePlayer::Exec 送到动画组件。此前 0x6f2ca9c 修改的是属性 26（紧密控球）。这里已找到能作用于跑动动作的入口，但没有用游戏计时验证“三档加速曲线”或具体百分比。
3. 长传只缩短触球前动作，在引擎结构上可实现：原生存在不中断当前动作的播放速率切换接口。需要绑定本次长传的实际出球事件并恢复原速；现有一次性倍率没有这种阶段控制。此结论是实现可行性和原生局部验证，不是已完成的游戏内效果。

一、真实射门偏差

实际调用链：
  0x6d42490 处理击球输出
    -> 0x6d42598 调用 0x6d52a04
         -> 0x6d53f2c 选择失误类别 / 判定
         -> 0x6d51d80 生成一组随机偏差
            或 0x6d51bd8 生成类别 3 的随机偏差
         -> 把偏差后的方向、仰角、速度转换回三维出球向量
    -> 0x6d425b4 调用 0x6d547d4，某些上下文继续修正出球向量

0x6d51d80 的主要输出位置：
  0x6d5237c：写入方向角；经 0x6910524 做原角度加偏差及角度回绕。
  0x6d5245c / 0x6d52630：写入仰角；原仰角加采样的有符号偏差。
  0x6d526bc：写入速度；原速度乘以 1 加有符号比例偏差。
0x6d51bd8 的对应输出位置：
  0x6d51c88：方向角。
  0x6d51d08：仰角。
  0x6d51d60：速度。
上述输出对象前三个 float 分别是方向角、仰角、速度，不能把第三个值也当成瞄准误差直接缩放。

受控原生执行结果：
  人工设置误差参数和随机数输入，名义值为方向 359 度、仰角 10 度、速度 100。
  负向随机数：输出约 349.7612 度、8 度、94。
  正向随机数：输出约 8.2388 度、12 度、106。
  换算最短方向差为 -9.2388 / +9.2388 度，仰角差为 -2 / +2 度，速度差约 -6 / +6。
  这是用于验证数据含义的合成输入；不是正常球员的典型射偏、技能增益或实测射正率。
  执行保留原生三角函数查表、角度回绕和浮点运算，只控制 RNG / 上下文；角度回绕所需标准 fmod 由等价宿主数学函数提供。

还须注意后处理：0x6d547d4 位于上述核心处理之后，0x6d54a94..0x6d54ac8 含条件性随机角度修正，0x6d54be4 / 0x6d54bf8 / 0x6d54c18 再写三维出球向量。
因此，后续若做“只减少实际瞄准散布”，应明确处理方向和仰角的随机增量，保持球速扰动的设计独立，并核对后处理分支。仅处理 0x6d52a04 中途保存的误差差值，不能证明覆盖最后的全部出球修正。

二、真实跑动加速入口及执行闭环

能力映射沿用已验证的原生表：
  比赛字段 44 -> 原始能力编号 11 -> 147 参数编号 38 -> 加速。
  比赛字段 40 -> 原始能力编号 10 -> 参数 34 -> 速度。
  比赛字段 26 -> 原始能力编号 3 -> 参数 19 -> 紧密控球。

真实加速系数构造函数：0x6f4d714。
  0x6f4d74c 调用 0x733cbbc，第三个参数 w2=0x2c，即字段 44。
  构造函数的模式参数为 0 时，普通受控上下文读取字段 44 并归一化；某些比赛上下文会合入其他能力，不能把所有返回值简单等同于原始面板。
  模式为 1 时，还读取字段 24（盘带），分别归一化后相乘，再开平方；因此带球分支同时受盘带能力影响。
  归一化来自真实的 0x6f4d6c4 -> 0x6f4d4e0。

实际执行链，不止预测：
  0x6dc4400（原生日志名 AnimePlayer::Exec）
    -> 在 0x6dc450c 调用当前状态处理器的虚函数 +0x28
    -> 普通移动状态 2 / 3 对应 0x6e758b4 / 0x6e75eec
    -> 0x6f4631c / 0x6f466c0 -> 0x6f40154
         -> 0x6f40b8c 调用 0x6f4d714，模式 0
         -> 返回值存到 sp+0x98，随后传到动作求解配置 +0x38，并参与后续动作选择、速率计算
         -> 0x6f45484 调用 0x6dccb08，下发选中动作和播放参数
    -> 0x6dc4400 读取待执行动作
    -> 0x6dc4714 调用动画组件的动作设置接口 0x678cd1c
    -> 0x6dc4730 调用真实播放速率接口 0x67902c0。

带球动作处理链：
  状态 4 / 5 / 6 的处理器虚表来自 0x98a8e38。
  每帧处理 0x6f14e3c -> 0x6f108b4；在 0x6f11ed4 调用 0x6f4d714，模式 1。
  该函数既包含预测与候选比较，也会在 0x6f12500 调用 0x6dccb08；所以修改共享辅助函数时必须区分真正下发动作的调用和仅作预测的调用。

可以继续用作后续设计的具体切入位置：
  普通跑动实际动作求解的加速输入：0x6f40b8c 调用返回之后。
  带球实际动作求解的加速输入：0x6f11ed4 调用返回之后。
  不能无条件修改所有 0x6f4d714 调用；它也被预测路径使用。
  更不能把玩家 +0x344 的当前速度当成加速度输入写回：0x69baf90 读取动画组件当前位置，根据相邻位置差计算测得速度，在 0x69bb044 写入 +0x344。这是位移结果的测量值。

这些是动作求解的无量纲输入，不是米/秒平方，也不是冲刺快了对应百分比。

三、长传能否只缩短前摇

现有倍率：0x6d5f640 处 s8 *= 1/0.88；0x6d5f2f0 将同一个 s8 写入选中记录 +0x18、+0x1c。
本次继续追踪到真正的动作记录转换：
  0x6d3d9f0 将这两个值复制到紧凑动作记录 +0x24、+0x28。
  0x6d3dab4 将紧凑记录保存到击球状态处理器 +0x80。
  0x6d3ec1c 使用第一个速率启动动作并做触球时间换算；0x6d4571c 的一个重新启动分支会使用第二个速率。
因此，不能仅凭两个字段就把它们命名为“前摇倍率 / 后摇倍率”，也不能认为只改其中一个必然保证另一阶段不变。
另外，玩家 +0x2a94 的 0x16c 大小动作记录是另一种结构，不能把它的 +0x18/+0x1c 误认成以上速率。

已确认可在动作中途改速率的接口：
  0x6ddbf6c(player, s0=rate)
    1. 保存当前速率到 player+0x4244；
    2. 获取动画组件 player+0xa88；
    3. 调用 0x67902c0(component, w1=0, w2=-1, s0=rate)。
  0x67902c0 更新已有动作轨道 +0x14 的播放速率，以及 +0x18 的速率倒数；随后更新相关缓存。
  这是原生中途调速接口，和重新设置动作 0x678cd1c 分开。

本次原生指令验证：
  使用两个已存在的合成动画轨道，执行 0x6ddbf6c -> 0x67902c0。
  设为 1.25 时，两条轨道的速率/倒数变为 1.25/0.8，其他轨道记录字节不变。
  再设为 1.0 时，两条轨道的记录恢复，其他字节仍不变。
  动画缓存刷新依赖使用桩或分支隔离；未运行完整渲染器，未作实机动画或触球录像验收。

阶段判断也有原生依据：
  0x6dbe318 读取动作中的击球事件时间。
  0x6dd8740 -> 0x6dda6c4 判断接近事件帧，按当前步长作时间窗口判断，并非简单比较“当前帧等于第 N 帧”。
  击球处理里的 0x6d4268c 增加 player+0x2a55 的触球阶段计数。
后续实现应绑定本次长传的实际出球事件，不能遇到任意控球触球就恢复；也不能只按固定帧数计时。

可行的分段方式（尚未实现）：
  选中符合技能条件的长传 -> 保存原生速率 R -> 触球前用 R*k -> 本次长传真正出球后恢复 R。
  动作取消、切换、失败回退时清理本次状态，避免影响下一动作。
  恢复 R，不能一律写死 1.0；原动作可能本来就有其他速率修正。
  实现时要同步核对动作记录、事件时间换算和当前播放速率，避免预测的触球时间与动画实际进度不一致。
  若目标为“前摇缩短 20%”，理想倍率 k=1.25。不能和现有整段 1/0.88 叠加后仍称前摇只缩短 20%。
  理想例：前摇 30 帧、后摇 20 帧，前摇 1.25 倍且触球后恢复原速，对应约 24+20 帧；整段 1.25 倍会变成约 24+16 帧。
  此例仅演示分段时间关系，实际动画事件落点受离散帧和原生事件处理影响。
